> 状态：**M1 已落地（2026-10-24）**——214 条命令/互操作层/随包运行库/测试/文档/四层 MCP 同步/双平台冒烟全绿（`npm run smoke:op`），stdio 8/8；M3 遗留真实目标补测（模拟器最小化截图/DX 窗口/dx 注入）。实施事实以本文为准，当日详情见 `更新记录/2026-10-24.md` OP 章节。
> 上游项目：https://github.com/WallBreaker2/op （MIT License，0.4.8.3，2026-07-07 发布）
> 评估与拍板日期：2026-10-23

## 一、背景与决策

### 1.1 为什么封装 op

op 是「大漠插件」的开源替代：把**后台窗口绑定、后台截图、找色找图、后台键鼠模拟、点阵字库 OCR、进程内存读写**整合在同一套 C API 里。LingBuilder 的用户群（易语言迁移用户、游戏脚本作者）与大漠插件的用户群高度重合，而大漠闭源、需注册、高级功能收费；op 是 MIT 协议、免注册、源码开放，零授权成本。

LingBuilder 现有图色模块（识图 / 截图 / opencv，见 `lingbuilder.image.recognition` 等）只覆盖**前台**场景。op 补齐的核心维度是**后台**：绑定目标窗口后，最小化、被遮挡、不在前台时依然可以截图、找图、收发输入——这是游戏脚本和自动化工具的刚需。

### 1.2 用户已拍板的三项决策（2026-10-23）

| 决策项 | 结论 |
|---|---|
| 分发方式 | **随包内置**（进 `builtinModules` 注册链，与 win32.basic 等内置模块同级） |
| 命令面规模 | **全量导出** C API（213 条，见 §3） |
| 通用 OCR | **不导出** op 的外部 HTTP OCR 引擎（`OpSetOcrEngine`，tesseract/paddle）——已有 `lingbuilder.ocr`（微信 OCR 借用，通用识别，19 条命令）覆盖该能力；**点阵字库 OCR 全部保留**（lingbuilder.ocr 替代不了游戏点阵字体） |

### 1.3 与现有模块的边界（共存不合并）

| 场景 | 用哪个 |
|---|---|
| 前台找图找色、无绑定需求 | 现有 识图 / 截图 / opencv 模块（更轻，无 DLL 依赖） |
| 通用文字识别（照片、截图里的自然文字） | `lingbuilder.ocr`（微信 OCR 借用） |
| **后台绑定**（最小化/遮挡窗口的截图与输入） | **本模块** |
| 游戏点阵字库识别 | **本模块**（字库族） |
| 游戏进程内存读写 | **本模块**（内存族） |

## 二、M0 已验证的事实（2026-10-23 真机）

SDK（x64/x86 zip）SHA256 与官方发布清单逐字一致。MSVC x64 编译探针，自建 Win32 窗口作绑定目标，闭环全绿：

- `OpCreate / OpVer / BindWindow(gdi,windows,windows) / GetColor / CmpColor / FindColor（精确命中）/ FindColorEx / FindMultiColor / Capture / LoadPic / FindPic（精确命中）/ GetScreenData / UnBindWindow` 全部通过。
- dumpbin 依赖核查：仅系统 API 集 + `d3d11.dll`/`dxgi.dll`（截图后端所需），**无 VC 运行库依赖（静态 CRT）**。

### 必须写进封装层的四个上游事实

1. **`op_c_api_x64.dll` 完全自包含**：不依赖 op_x64.dll（那是 COM 路线的组件），静态 CRT。每架构只需随包分发一个 DLL：x64 约 10.3MB、x86 约 10MB。
2. **FindPic/FindPicEx 返回值是模板编号**（命中第 N 个模板返回 N，首个=0；失败返回 -1），不是「1 成功/0 失败」。我们的命令层统一翻译成 1/0（多模板时如需知道命中哪个，用找图Ex 的字符串结果）。
3. **截图区域右/下边界是开区间**：`Capture(0,0,399,299)` 得到 399×299 的图。与大漠的闭区间（x2-x1+1）不同，命令文档必须显著标注。
4. **颜色格式为 RRGGBB**：`GetColor` 对红色返回 `"FF0000"`。大漠是 BBGGRR（`"0000FF"`=红）。这是给大漠迁移用户的重点差异提示。

另有两条行为备注：相似度参数语义与大漠一致（0~1，内部自动重映射）；`GetPicSize` 只认「全局路径 + 相对文件名」（M1 实现时钉死用法）。

### 工程注意点

- **头文件必须钉 release tag**：master 分支已漂移（`OpVer` 签名已改），与 0.4.8.3 的 DLL 不配套。一律使用 0.4.8.3 tag 的 `op_c_api.h`。
- 本机网络配方：github.com 的 release/raw CDN 不通，下载走 `api.github.com`（资产端点 + `Accept: application/octet-stream`；源码走 contents API + `Accept: application/vnd.github.raw`）。
- SDK 与探针存档：`.zcode/tmp/op-sdk/`（0.4.8.3 解包、m0/ 探针三只与构建脚本）。

## 三、封装后的能力全景（213 条命令）

> 命令命名：「后台_」前缀中文主名 + 大漠英文别名（如 `后台_绑定窗口` alias `BindWindow`），方便大漠老用户按肌肉记忆检索。以下按命令族给出能力说明，条数为该族命令数。

### 3.1 后台窗口绑定（6 条）——本模块的灵魂

| 能力 | 说明 |
|---|---|
| 绑定后台窗口 | 指定截图后端与键鼠模式绑定目标窗口；支持 `normal`（前台）、`gdi/gdi2`、`dxgi`、`wgc`（Win10 1903+）、`dx.d3d9/d3d10/d3d11/d3d12`、`opengl`（含 `opengl.nox` 夜神专用）、`normal.auto`（自动选型） |
| 显示/输入分离 | `BindWindowEx` 允许「截图窗口」和「接收键鼠的窗口」是两个不同句柄——嵌套窗口、模拟器、浏览器控件场景的解法 |
| 后台输入锁定 | `LockInput` 锁定真实键鼠（全部/仅鼠标/仅键盘），脚本跑着不影响人用电脑 |
| 绑定状态查询 | 是否已绑定、取绑定句柄、解绑 |

**用户得到什么**：窗口最小化、被其他窗口盖住、甚至切到别的桌面，脚本照样对它截图找图、收发键鼠。

### 3.2 窗口与进程（41 条）

枚举窗口/进程、按进程名或 PID 找窗口、取窗口类名/标题/状态/矩形/客户区尺寸、移动窗口、调整窗口大小、设置窗口透明度、发送文本与粘贴、**批量窗口排列布局**（行列网格、间距、锚点）、前台窗口查询、坐标换算（客户区↔屏幕）、剪贴板读写、运行程序并取命令行输出、精确/随机延迟。

### 3.3 后台鼠标（35 条）

- 移动：绝对/相对移动、**平滑移动**（带时长）、区域内随机移动（MoveToEx）、**轨迹移动**（多点路径）、**拖拽路径**、**拟人化轨迹配置**（时长范围、抖动、起止延迟）。
- 按键：左/中/右/X1/X2 五键位 × 单击/双击/按下/弹起 = 20 条。
- 滚轮：垂直/水平 + 上/下便捷命令。

**用户得到什么**：点击、拖拽、滑动力全都发往后台窗口，配合拟人轨迹降低检测特征。

### 3.4 后台键盘（10 条）

按下/弹起/单击（虚拟键码）、按字符串按键（字符形态）、按字符串连发（带间隔）、按键状态查询、等待某键出现、按下/弹起延迟配置。

### 3.5 图色核心（22 条）

区域截图存盘、单点取色/比色、找色/多结果找色、**多点找色**（首色+偏移色组合特征）、色块找色、颜色计数、**多模板找图**（一次找多个图，返回命中模板与坐标）、透明色模板、图片预加载/释放/**内存图片加载**（字节集直接当模板）、模板尺寸查询、**裸屏幕数据**（GetScreenData 返回像素指针，可喂给自定义算法）。

### 3.6 OpenCV 高级图色（35 条）

- 模板匹配 6 种：普通匹配、**掩码模板**（遮住干扰区域）、多模板任一/全部匹配、**特征点匹配**（缩放旋转鲁棒）、边缘匹配、形状匹配、**缩放匹配**（多尺度找图）。
- 图像预处理 14 种：灰度、二值化、边缘、轮廓提取、去噪、直方图均衡、CLAHE、锐化、腐蚀膨胀（形态学）、细化、阈值、通道范围、裁剪、缩放、有效区域裁剪、**预处理管线**（一条命令串多个步骤）。
- 模板库管理：按名字加载/卸载/清点/列举。

### 3.7 点阵字库 OCR（35 条）——大漠资产直接复用

- **字库管理**（9 条）：从文件加载字库、**从内存加载字库**、增加/清除条目、保存字库、切换当前字库、字库计数、取当前字库。
- **识字**（3 条）：区域内识字（返回文本）、识字并返回每条坐标（Ex）、**自动识字**（OcrAuto，免颜色描述）。
- **找字**（2 条）：区域内找指定字符串返回坐标。
- **词组抓取**（7 条）：抓取指定词的精确位置、按宽高提取词框、按给定矩形框批量取词。
- **无字库取词**（1 条）：GetWordsNoDict，不加载字库直接切出词块（配合自定义识别）。
- **字库调试工具**（6 条）：二值化预览、单字预览、字库校验、字库规范化、字库改名、二值化预处理配置——做字库调参时的眼睛。
- **结果读取**（3 条）：识字结果计数/取坐标/取文本。
- **辅助**（4 条）：找直线（FindLine，寻路用）、从文件识字/自动识字（截图文件直接识字）。

**兼容性**：兼容大漠文本点阵字库格式，用户手头的 dm 字库资产直接喂进来就能用。字库还支持内存加载（字节集），配合网络下载字库不用落盘。

### 3.8 内存读写（10 条）

对绑定窗口（或指定窗口句柄）的进程：读写字节集、读写整数（含类型宽度）、读写单精度/双精度浮点、读写字符串。地址支持模块偏移表达式形态。配合多级指针即可做常规游戏内存脚本。

### 3.9 YOLO 目标检测（3 条）

配置检测引擎、按区域检测、按图片文件检测。**注意：引擎是外部 Python 服务**（上游提供 `op_yolo_engine.py`），命令文档会写清启动方法；不用 YOLO 的用户完全不受影响。

### 3.10 算法（2 条）

A 星寻路（给地图障碍点集，算最短路径）、最近点选取（一堆候选点里找离我最近的）。

### 3.11 生命周期与基础（14 条）

创建/销毁 OP 句柄、设置全局路径（图片/字库根目录）、版本查询、错误码查询（命令层配中文错误文本）、图片缓存开关、截屏数据模式、延时、DLL 注入（高级）。

### 3.12 不导出（1 条）

`OpSetOcrEngine`（外部 HTTP 通用 OCR 引擎切换）——由 `lingbuilder.ocr` 承担通用 OCR。

## 四、技术方案

### 4.1 模块定义

| 项 | 值 |
|---|---|
| 模块 ID | `lingbuilder.op` |
| 中文名 | 后台图色（暂定，M1 定稿） |
| 版本 | 1.0.0 |
| 上游版本 | op 0.4.8.3（钉死，升级需重跑 M0 全套回归） |
| 目标 | `windows-msvc-win32`（带 x86 DLL）/ `windows-msvc-x64`（带 x64 DLL） |
| 句柄类型 | `OP句柄`（long long 封装，`后台_创建` 返回） |
| 文档 | `docs/modules/op/README.md`（随包文档门禁覆盖） |

### 4.2 运行时分发（已核实的现成机制）

- DLL 实体入库：`electron/third_party/op/x64/op_c_api_x64.dll` + `electron/third_party/op/x86/op_c_api_x86.dll`（**每架构一个文件**，上游 MIT 允许随包再分发，LICENSE 一并入库）。
- manifest `targets[].runtimeFiles` 按架构声明（`excelModule.ts` / `mysqlModule.ts` 就是每架构一个 DLL 的现成样板）。
- `nativeDependencyService.ts` 新增 `materializeOpRuntime`，构建时把对应架构 DLL 物化到生成工程输出目录。
- 安装包体积增量约 +20MB（x64+x86 双份），相对 CEF 级体积可接受。

### 4.3 代码生成与互操作

- 命令定义集中在 `electron/src/services/modules/opModules.ts`（createStandardModule 工厂，先例同 wxocr/ocr 模块）。
- 生成的 C++ 侧走 **LoadLibrary/GetProcAddress 互操作层**（免 `.lib` 链接，wxocr blob 先例形态）：按架构动态解析 DLL 名，启动时懒加载，函数指针表 + stdcall 签名与 0.4.8.3 头文件一一对应。
- **FindPic 返回值翻译**在命令层完成（pic_id/-1 → 1/0），用户面永远是大漠习惯的 1/0。
- **中文错误文本**：OpGetLastError 只给错误码，互操作层维护码表映射，`后台_取错误()` 返回中文。
- 本模块全部参数都是数值/文本/字节集，**无 controlRef 参数**、无处理器回调（全同步命令），门禁面干净。

### 4.4 双后端

与所有内置模块一致，命令同时服务普通 Win32 后端与 new_emoji 后端（fragments 数组各加一行互操作 runtime 注入）。

## 六、风险与边界

| 风险 | 评估与对策 |
|---|---|
| 杀软误报 | dx 输入模式属注入类，误报概率高；与 NSIS 安装包「未签名误报属正常」立场一致，文档标注。纯 gdi/wgc 截图 + windows 消息输入不涉注入。 |
| 模拟器/游戏兼容 | 截图后端是否对某游戏生效因目标而异（这就是 op 提供多后端的原因）；M3 真机补测雷电/夜神，文档给「后端选型速查」。 |
| 上游停更 | MIT + 0.4.8.3 已存档，可 fork 自养；版本钉死不受上游漂移影响。 |
| 位数约束 | op DLL 与生成 exe 必须同位数——runtimeFiles 按目标架构分发天然保证。 |
| YOLO 依赖外部服务 | 3 条命令文档写清引擎启动方法；主流程零依赖。 |
| 体积 | +20MB 安装包（双架构），一次性成本。 |

## 七、验收标准（复述硬门禁）

1. `npm run build` 通过；`tests/modules.test.ts`（命令面 + 内置文档门禁 + 审计基线）通过。
2. 双平台 MSVC 真机编译、smoke 全绿（含真实模拟器最小化截图闭环）。
3. IDE 全链：新建项目 → 写 `后台_绑定窗口` → `后台_找图` → F5 运行，行为与生成 C++ 导出工程一致。
4. 四层 MCP 同步落地且 stdio 握手验收通过；AI（外部 AI 经 Bridge）能按正确口径生成后台图色代码。
