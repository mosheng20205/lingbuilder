# 二维码模块（lingbuilder.qrcode）使用说明

纯本地实现的 QR Code 生成与识别模块，遵循 ISO/IEC 18004（QR Code Model 2）。算法、PNG/JPEG 编解码、图像定位全部自带，不依赖任何第三方运行时（Python / Node / 浏览器内核）、第三方图像库或在线 API；生成与识别可互相闭环自校验。

- 生成：数字 / 字母数字 / 字节(UTF-8) 三种模式自动择短，版本 1-40 自动选最小可容纳者，纠错级别 L/M/Q/H 可选。
- 识别：定位图形游程定位 → 三点配对 → 对齐图形精化单应 → 重采样 → 去掩码 → 反交织 → RS 真纠错（不止校验）→ 分段解码。

## 类型

| 类型 | 说明 |
| --- | --- |
| 二维码句柄 | `二维码_生成` 返回的受管对象，持矩阵、版本、掩码、级别与位图缓存；必须显式 `二维码_释放`。 |
| 二维码识别结果 | 识别命令返回的受管结果；必须显式 `二维码_识别释放`。 |

## 中文错误清单

生成侧（`二维码_取错误`）：

- 内容为空，无法生成二维码。
- 内容过长（UTF-8 超过 4096 字节），超出二维码容量。
- 纠错级别无效：只允许 L、M、Q、H。
- 边长像素必须大于 0（默认 8）。／边长像素过大：上限 64（默认 8）。
- 空白边模块数越界：允许 0～32（默认 4）。
- 内容超出 40-H 版本容量（最长约 1273 字节），无法生成二维码。
- 输出边长 N 像素超过 4096 上限，请减小边长像素或空白边模块数。
- 二维码句柄无效（可能已释放）。
- 无法写入文件（路径或权限问题）：…
- 自检失败：…（附具体原因）

识别侧（`二维码_识别取错误`）：

- 图像太小：至少需要 21×21 像素。
- 不是有效的 PNG 文件。／不是有效的 JPEG 文件。
- 不支持的图像格式：二维码模块只内置 PNG 与 JPEG（基线）解码。
- 暂不支持隔行（Adam7）PNG。／不支持的 PNG 位深 N。／PNG …损坏／不完整。
- 暂不支持渐进式（Progressive）JPEG。／JPEG 霍夫曼解码失败。／JPEG 位流提前结束。
- 宽度与高度必须大于 0。／通道数只支持 1（灰度）、3（BGR）、4（BGRX）。
- 字节集长度 N 与 宽×高×通道数 M 不一致。
- 截图区域越界：屏幕为 W×H，请求区域 …
- 未识别到二维码：图像中找不到三个定位图形（可能没有二维码或损伤过重）。
- 未识别到二维码：定位图形无法配对成有效的二维码区域。
- 格式信息损坏：无法从 format 区恢复纠错级别与掩码号。
- 纠错失败：码字损伤超出该纠错级别的能力（块 X/Y）。
- 结果句柄相关命令在句柄无效时按说明返回空文本 / -1 / 假。

## 算法口径（ISO/IEC 18004，逐条可校验）

生成：

- 模式自动择短：全数字 → 数字模式；否则全字母数字字符集（0-9 A-Z 空格 `$%*+-./:`）→ 字母数字模式；否则字节模式（UTF-8）。版本选择取「该模式下能容纳的最小版本」。
- RS：GF(256)，本原多项式 0x11D，生成元 α=2；分块/交织按标准表（与 nayuki qrcodegen 表逐项核对，M 级 v1-20 另与仓库参考实现逐项核对）。
- format：5 位数据 = (级别位 << 3) | 掩码，级别位 L=01 M=00 Q=11 H=10；BCH(15,5) 生成多项式 0x537，整体 XOR 0x5412。已知答案：M+掩码0 = 0x5412，M+掩码3 = 0x5B4B。
- version（v≥7）：BCH(18,6) 生成多项式 0x1F25。
- 功能图形：3 组定位图形+分隔符、row6/col6 定位线、各版本对齐图形坐标表（nayuki 公式，与标准表逐版本一致）、黑点固定在 (4·版本+9, 8)。
- 数据放置：右下角起两列蛇形、上下交替，遇第 6 列整体左移；掩码只作用于数据区。
- 掩码选择：8 掩码全试，按标准四条罚分规则取最低分（N1 同色行/列长 ≥5、N2 2×2 同色块、N3 1:1:3:1:1:1:1 图案、N4 深色占比五级步进）。

识别：

- **Tier A｜网格直读**：输入是干净的正方形码图（如本模块自己出的 PNG，或 N×N 矩阵直解字节集）。Otsu 二值化 → 定位图形 1:1:3:1:1 游程定位（横竖交叉校验+聚类）→ 三点配对反解模块数与空白边 → 单应重采样按模块中心 9 点最近像素采样 → format BCH 反推级别+掩码 → 去掩码 → 反交织 → RS 纠错 → 出文本。
- **Tier B｜真实图像**：同一套定位管线直接吃照片级输入；对齐图形用 5×5 理想图案匹配精化第 4 点得到真单应（透视），配 ±1 版的模块数容差、双阈值二值化（大津/自适应）、三级网格阈值（网格 Otsu → 全图 Otsu → 128）与「小模块图 3 倍放大重试」。实测抗性：缩放到 0.4×、旋转 ±8°、高斯模糊 σ1.5、JPEG q60（基线）均能解出并如实报告修复码字数。
- 两层走同一套 RS 纠错（Berlekamp-Massey + 钱搜索 + Forney，非只验不修），修复码字数如实累加上报。

## 自检（二维码_自检）

`二维码_自检()` 返回真表示全部通过：

1. format 已知答案：M+掩码0 = 0x5412、M+掩码3 = 0x5B4B。
2. "HELLO WORLD"（字节模式）→ 版本 1-M、21 模块。
3. M 级 v1-20 每版本数据码字数与标准表逐项核对。
4. 全部 160 组（40 版本 × 4 级别）：满容量编码后每块 RS 伴随式全零。
5. 10 版本 × 4 级别「生成 → 栅格化 → 识别」闭环：文本逐字节一致、版本/掩码/级别一致。
6. 带损伤纠错：对 v5-M 扰动 6 个模块后仍原样解出。

## 验证记录（2026-10-01，x64 与 win32 双架构同结论）

- 自检、已知答案 4 项、回读覆盖 24 组×双通道（PNG 落盘 + 矩阵直解字节集，含 ASCII/中文 UTF-8/emoji/长 URL/纯数字/字母数字/转义敏感串/中文标点/多级别/多边长）48 项、数据区扰动 12 项、Tier B 四退化（0.4× 缩放、旋转 ±8°、高斯模糊 σ1.5、JPEG q60）全部通过。
- 独立标准解码器交叉验证：jsQR 对本模块 5 组对拍载荷（1/11/40/175/300 字节）渲染出的码逐字节解出原文。
- x64 与 win32 的矩阵导出（版本/掩码/FNV-1a 矩阵哈希）完全一致。

### 与仓库参考实现（T:\逆向\小红书\tools\qr-encode.mjs）的关系

该参考实现的 format BCH、RS 编码、罚分函数与分块表均正确（本模块已逐项核对），但其 `toCodewords` 存在位/字节混淆（`buildBits` 返回比特数组却被按码字字节切片，RS 按比特值当字节计算，最后又按 8 位展开），导致其矩阵数据区不是合法 QR 数据——jsQR 解其码只能得到空文本。因此本模块的矩阵不与其逐位对拍，改用更强的独立标准验证：jsQR 对本模块全部对拍载荷逐字节还原（版本号选择口径与参考一致，掩码号因两者矩阵数据区不同而不可比）。已知答案 1-4 与该参考重合的部分（format 位串、版本/尺寸）逐位一致。

## 已知边界

- PNG 解码不支持隔行（Adam7）；JPEG 解码支持基线（SOF0/1），不支持渐进式与算术编码；16 位量化表取高字节近似。
- ECI 段跳过（不换码页）；结构化附加（Structured Append）未拼合，各段独立解码。
- 识别一次解码一个最可信候选；多码图取分最高者。
- `二维码_识别屏幕` 依赖进程 DPI 意识：DPI 不感知进程按虚拟化坐标解释参数。
- 设计器控件「二维码框」暂未提供（规划二期）；当前用 `二维码_保存PNG` + `控件_设置图片` 或 `二维码_取位图` + `STM_SETIMAGE` 显示。
